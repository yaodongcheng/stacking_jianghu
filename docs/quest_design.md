# 任务系统设计

## 一、设计目标

任务系统服务于游戏的"目标牵引力"和"决策密度"两个核心体验：

- **目标牵引力**：玩家任何时候都能在任务卡上看到"我现在该做什么、做完有什么"，这是长期留存的基础设施。
- **决策密度**：任务不是简单的「做 → 拿奖励」流水线，而是给玩家可以权衡的选择——接不接、何时接、用多少本钱、是否冒险求超额。

围绕这两点，本设计从两个视角切入：
- **用户体验视角**：玩家看到的任务卡格式统一、信息密度恰当、关键决策点（接取/进行中/结算）有清晰的节奏。
- **结构优雅视角**：数据驱动、字段可选、按任务族派发结算逻辑，避免老任务被新字段污染、新任务被无关字段绑架。

---

## 二、任务三大族

任务在本质上不是"一种东西"。当前 51 个任务里至少有三类不同的结构，强行统一只会得到一件紧身衣。

| 任务族 | 特征 | 涉及 type | 关键字段 | 不适用字段 |
|---|---|---|---|---|
| **委托型 (Commission)** | 主动接取、有本金、量化产出、可超额 | GATHER / RECRUIT / RESOURCE_TOTAL / HAVE_UNIT | budget + count(预期) + reward + deadline + 曲线 | — |
| **剧情型 (Narrative)** | 0/1 完成、推进叙事、无量化 | DIALOG / INTERACT / REACH / COMBAT / CHOICE / DELIVER / GOAL | reward(固定，可缺省) | budget / 曲线（无意义） |
| **生存/触发型 (Passive)** | 时间或状态被动触发，无玩家明确执行步骤 | SURVIVE / WAIT_TIME / EAT / FREE | desc 自描述即可 | budget / reward / deadline 多数为空 |

**判别原则**：任务的 type 决定它属于哪族，结算器和 UI 渲染按族派发，不需要在配置上额外标记。

## 三、CSV 数据结构

### 3.1 现有字段（保留）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | 任务唯一 ID |
| title | string | 任务标题 |
| scenario | string | 任务场景分类（TUTORIAL / SANDBOX 等） |
| type | enum | 任务执行类型（决定属于哪族） |
| target | string | 任务目标对象（含义随 type 变化：物品 ID / NPC 名 / 坐标 / 时辰等） |
| count | int | 量化任务的**预期产出**（委托型）或目标数量（剧情型） |
| next | string | 后续任务 ID，分支用 `GOOD:Q1\|EVIL:Q2` 格式 |
| desc | string | 任务描述文本（UI 主行） |
| submit_npc | string | 任务发布/交付人（`9999` = 自动完成） |

### 3.2 新增字段（全部可选）

| 字段 | 类型 | 说明 | 适用任务族 |
|---|---|---|---|
| **budget** | string DSL | 接取时**立刻发放**的本金（硬上限，花完即止） | 委托型 |
| **reward** | string DSL | 完成时的**基准奖赏**（1.0 倍达成时的标准值） | 委托型 / 剧情型 |
| **deadline** | int | 期限（接取后的相对天数） | 委托型 / 部分剧情型 |

### 3.3 reward / budget DSL 规范

统一格式：`类型:数值` 用 `;` 分隔多项。

```
MONEY:300                              # 单一项
MONEY:200;FAME:10;MERIT:5              # 多项
MONEY:200;ITEM:生鱼:3                  # 物品带数量
```

支持的类型：`MONEY` / `FAME` / `MERIT` / `ITEM:<物品名>`

### 3.4 字段填法对照

```csv
# 委托型 - 全字段
Q_PROCURE_RICE,采办军粮,SANDBOX,GATHER,粳米,100,Q_NEXT,为军营采办100石粳米,师爷,MONEY:300,MERIT:5;MONEY:200,5

# 剧情型 - 只填基本字段，奖赏可缺省
Q_FIND_FISHER,堆叠到果树,SANDBOX,REACH,果树,1,Q_NEXT,堆叠到果树查看,9999,,,

# 生存型 - 大部分字段为空
Q_SURVIVE_10,撑过十日,TUTORIAL,SURVIVE,DAY,10,Q_END,生存满10天,9999,,,
```

**核心规则：字段为空 = "不适用"**，不需要默认值，不需要占位符。

## 四、UI 呈现规范

### 4.1 核心原则：侧边栏极简，深度信息分时机呈现

侧边栏的任务卡是"我现在该做什么"的扫读提示，不是任务详情面板。所有任务都显示一张卡，**卡上只有任务名 + 描述**，没有点击展开的二级面板。

委托型任务的本金/期限/奖赏曲线等丰富信息**不在卡片上常驻**，而是在以下时机集中呈现：
- **接取对话面板**——玩家做"接不接"决策时
- **结算对话**——任务完成时戏剧性揭示

这种分时机呈现的取舍：牺牲了实时反馈，换来侧边栏始终清爽 + 决策信息聚焦在该出现的时刻。

### 4.2 任务卡片设计

侧边栏卡片只有两要素：**任务名（title）+ 描述（desc）**。量化进度直接拼到描述末尾，状态用颜色编码而非额外文字行。

**剧情型 / 生存型示例：**

```
┌────────────────────────┐
│ 寻访村长                │
│ 堆叠到果树查看           │
└────────────────────────┘
```

**委托型 / 量化进度示例：**

```
┌────────────────────────┐
│ 采办军粮                │
│ 为军营采办粳米 (3/100)   │
└────────────────────────┘
```

### 4.3 状态颜色编码

| 内部状态 | 视觉表现 |
|---|---|
| AVAILABLE | 不在侧边栏显示（未接取） |
| ACTIVE | 默认色 |
| ACTIVE + is_urgent | 红色边框 + 倒计时角标（临期 / 资源告急） |
| READY | 金色高亮 + ✦ 前缀（可交付） |
| COMPLETED | 渐隐后从列表移除 |

### 4.4 任务卡优先级排序

侧边栏多任务并存时按以下优先级排序（高→低）：

1. 生存型（饥饿、寒冷等危险警告）
2. 委托型（有期限的事务）
3. 剧情型主线
4. 剧情型支线

## 五、委托型任务：太阁式结算

委托型任务是当前任务系统最缺的"决策密度"来源，参考太阁立志传的差遣办差机制。

### 5.1 核心概念

> **"本金是硬上限，成果是浮动的。"**

玩家的决策密度全部转移到「怎么把这 300 文用出 600 文的效果」上，而不是花多少。

- `budget` = 接取时一次性发放给玩家的本金，花完即止，**不存在超支**
- `count` = 委托人的**预期产出**（基准线），完成 = 达到 1.0 倍
- `reward` = 1.0 倍达成时的**基准奖赏**
- 实际奖赏 = `reward × 完成度倍率`（按曲线计算）

### 5.2 完成度奖赏曲线（默认值，全局可调）

| 完成度 ratio = actual/count | 奖赏倍率 | 叙事感 |
|---|---|---|
| < 50% | 0x（无功） | 「办事不力」 |
| 50–99% | 0.5x | 勉强交差 |
| 100% | 1.0x | 称职 |
| 100–150% | 2.0x | 「干得漂亮」 |
| 150–200% | 3.0x | 「真乃栋梁」 |
| ≥ 200% | 4.0x | 「绝品差事」 |

注：曲线本身不直接扣分，**惩罚仅在"未完成又吞了本金"时才触发**——见 5.5。

### 5.3 三个 UX 节点

**节点 1：接取对话面板**

```
师爷：城南军营缺粮，需采办 100 石粳米。
师爷：本官拨付本金 300 文，限 5 日内办妥。
师爷：办成赏功勋 5 点、银钱 200 文。
      若办得格外漂亮，另有重赏。

[接受委托]  [我再想想]
```

决策三要素一屏看清：**代价 / 期限 / 收益**。

**节点 2：进行中的侧边栏卡片**

侧边栏卡片**只显示任务名 + 描述（含进度）**，状态颜色编码（详见 4.2）。本金余额、倒计时数字等丰富信息不在卡片上常驻——这是为了保持侧边栏极简。临期或资源告急时，is_urgent 状态触发红色边框 + 倒计时角标作为唯一的紧迫感提示。

**节点 3：完成结算对话**

戏剧性的高光时刻：

```
师爷：你只领了 300 文本钱去……
       (停顿)
师爷：竟采办回 200 石粳米？！
       这是预期的两倍啊！

[功勋 +20  (基准 5 × 4 倍超额奖励)]
[银钱 +800 (基准 200 × 4 倍超额奖励)]
```

数字弹窗 + 台词 + 音效三连击，是玩家会记住的「我办成了一件大事」的瞬间。

### 5.4 适用范围

只对**可量化产出**的任务有意义：

- ✅ GATHER（采购粮草、收集药材）
- ✅ RECRUIT（招募浪人、收拢流民）
- ✅ RESOURCE_TOTAL（筹银、积粮）
- ✅ HAVE_UNIT（建造房屋、雇佣工匠）
- ❌ DIALOG / INTERACT / REACH / CHOICE / COMBAT(boss) / DELIVER / GOAL —— 这些是 0/1 完成的剧情型，固定 reward 即可

**配置层判别规则**：填了 `budget` 就走太阁式结算，没填就走简单结算。零额外字段、向后兼容。

### 5.5 本金归属与失败惩罚

**本金归属规则：**
- 任务完成（≥100%）：剩余本金归玩家所有，理所当然。
- 任务未完成（<100%）：结算对话给玩家选择——上交剩余本金给委托人，或私自留下。

**失败惩罚公式：**

```
惩罚功勋 = 基准奖赏 × (1 - 完成度) × (未上交本金 / 本金总额)
```

两个锚点（用户决议）：

| 完成度 | 全部上交本金 | 全部留下本金 |
|---|---|---|
| 0%（彻底失败） | **0 功勋（无功无过）** | **-基准奖赏（贪污受罚）** |

中间情况自然插值：完成度越高、上交越多，惩罚越轻。

**完整结算矩阵示例（基准奖赏 = 5 功勋）：**

| 完成度 | 全部上交本金 | 全部保留本金 |
|---|---|---|
| 0%   | 0 功勋 | -5 功勋（贪污） |
| 50%  | +2.5 功勋 | +2.5 - 1.25 = +1.25 功勋 |
| 100% | +5 功勋 | +5 功勋（剩余归己，理所当然）|
| 200% | +20 功勋 | +20 功勋（剩余归己）|

**叙事感**：这个机制把"贪污"作为玩家的主动选择呈现，而不是系统强加的惩罚。诚信失败 = 体面退还，无功也无过；贪污失败 = 道德污点，遭到弹劾。完全契合宋代官场「不患无能患贪婪」的治政逻辑。

**结算对话 UX 示例（失败 + 选择）：**

```
师爷：……你只采办回 30 石粳米，远不及预期。
师爷：本金 300 文，你还剩 200 文。
师爷：(目光锐利) 这 200 文，你打算如何处置？

[全数上交]                  ← 0 功勋
[留作辛苦费]                 ← -3 功勋（贪污）
[上交一半，留一半]           ← -1.5 功勋
```

## 六、实现契约

### 6.1 数据层

- 单张 `data/quest_config.csv`，字段全部 nullable
- 新加任务只填相关列，空格 = "不适用"
- DSL 解析独立成函数，便于复用与测试

### 6.2 代码层

```
QuestSettlement (工厂)
    │
    ├─ CommissionSettlement   ← 任务有 budget 字段
    ├─ NarrativeSettlement    ← 默认剧情型
    └─ PassiveSettlement      ← SURVIVE / WAIT_TIME / EAT / FREE
```

每个结算器只看自己关心的字段，不出现 `if task.type == X: ...` 的类型分支污染。

### 6.3 UI 层

侧边栏卡片只渲染两要素：`title` + `desc`（量化任务把进度拼到 `desc` 末尾）。委托型任务的本金/期限/奖赏不进入侧边栏，而是在接取对话面板和结算对话里独立呈现。

`TaskDisplayData` 仍保留 Optional 字段（`reward` / `deadline_days` / `budget` 等），供以下用途：
- 接取对话面板和结算对话从此读取并渲染
- 计算 `is_urgent` 状态（如本金告急、期限临近）
- 未来如果加 tooltip / 详情弹层，数据现成

**好处：**
- 老任务不需要为新字段做兼容（侧边栏渲染不依赖任何新字段）
- 新任务不需要思考"我要不要填这个字段"——填了就在对话面板呈现，没填就缺省
- 所有任务族共用同一个侧边栏渲染器

### 6.4 向后兼容

本设计的实施分两步：

1. **第一步（结构准备）**：增加 3 个可选字段到 CSV，改 `TaskDisplayData` 字段为 Optional，改渲染器为"按字段渲染"。**所有现有任务行为不变**（新字段都为空，结算逻辑不变）。
2. **第二步（委托型落地）**：实现 `CommissionSettlement`、本金发放、曲线奖赏、三节点 UX。开始把现有 `REWARD_*` action 迁移到数据列。

## 附录：已决议项（备忘）

为保留设计推演的脉络，以下是讨论中已经敲定的关键决策：

- **接取前详情面板**：不做。侧边栏只显示任务名 + 描述，深度信息在接取对话和结算对话呈现。
- **本金归属**：剩余本金归任务执行者（玩家）所有。完成时无条件归己；未完成时由玩家选择上交或留下。
- **失败惩罚的尺度**：用"完成 0% + 全部上交本金 = 0 功勋"和"完成 0% + 全部留下本金 = -基准奖赏"两个锚点，中间情况按公式插值。曲线本身不直接扣分，只在贪污时触发惩罚。
